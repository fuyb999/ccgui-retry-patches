# CC GUI v0.5.2 Long-Session Structured Stream Design

## Problem

Codex structured replay is working in the Node bridge, but long-running CC GUI
conversations can still show only streaming text. The affected runtime session
contained more than 32,000 UI messages and 218 tool calls in one Codex turn.

`CodexMessageHandler` keeps the turn's thinking and `tool_use` blocks in one
assistant message while appending each `tool_result` as a later user message.
`StreamMessageCoalescer` transports only the last 180 messages once a
conversation is long. After 180 tool results, the mutable assistant message is
outside that tail, so its new thinking and tool blocks no longer reach the
WebView. Small `onContentDelta` calls continue to arrive, producing the observed
text-only stream.

## Goals

- Keep current-turn thinking and tool blocks visible after any number of tool
  results in a long conversation.
- Preserve the bounded 180-message tail transport and its existing history,
  sequence, and compaction behavior.
- Avoid sending the entire conversation or expanding the tail back to the
  current turn's first assistant message.
- Keep the change compatible with existing three-argument
  `window.updateMessageTail` callers.

## Non-Goals

- Changing Codex retry classification, retry delays, or inactivity deadlines.
- Replacing JSONL structured replay or changing its three-second polling
  interval.
- Redesigning the session message model into alternating assistant segments.
- Adding a new general-purpose event protocol for every content block type.

## Design

### Sparse Assistant Anchor

For a stable long-conversation tail update, `StreamMessageCoalescer` will locate
the last assistant message before the selected tail base. It will attach that
message and its absolute backend index as an optional sparse anchor in the same
`updateMessageTail` JavaScript call.

The normal tail remains unchanged. No anchor is sent for a full snapshot or when
the last assistant is already inside the transported tail.

### WebView Merge

`window.updateMessageTail` will accept two optional trailing arguments:

1. serialized anchor message
2. absolute anchor index

The WebView will first construct the usual tail result, then replace the message
at the anchor's absolute backend index when that index is addressable in the
current local window. Prepended history is accounted for separately from backend
indices.

If the anchor is absent, malformed, stale, outside the available local window,
or not an assistant message, it is ignored. The existing tail update still
applies. This makes the protocol backward compatible and prevents a bad sparse
patch from corrupting the message list.

### Ordering And State

The anchor and tail share one transport sequence and one JavaScript invocation.
The existing minimum-sequence guard therefore accepts or rejects them together.
After merging, existing optimistic-message preservation, streaming content
preservation, turn metadata reconstruction, and duplicate-tool cleanup run on
the combined result.

The anchor updates the current assistant's raw block list, while the tail
continues to carry recent `tool_result` messages. The frontend can therefore
render the correct thinking/tool sequence without receiving the unchanged
32,000-message prefix.

## Error Handling

- Java sends no anchor when it cannot identify an omitted assistant message.
- WebView parsing failures are contained to the anchor; a valid tail is still
  processed.
- Invalid indices and non-assistant anchors are ignored.
- Existing full-snapshot fallback remains authoritative after shrink,
  compaction, prefix replacement, or first delivery.

## Testing

### Java

- A stable long conversation whose current assistant lies before the last 180
  messages selects tail transport plus that assistant anchor.
- No redundant anchor is selected when the assistant is already in the tail.
- Existing first-snapshot, threshold, growth, shrink, and replaced-prefix tests
  remain unchanged in behavior.

### WebView

- A tail update patches an assistant anchor outside the tail while retaining the
  full prefix.
- Prepended history does not shift the anchor's backend index incorrectly.
- Invalid, stale, and malformed anchors do not block the normal tail update.
- Existing streaming, message synchronization, and full WebView suites pass.

## Release

The fix will be released as `0.5.2-retry.4`. The version-specific patch,
manifest, README, verification scripts, plugin ZIP, and SHA-256 checksum will be
updated together. Installation and IDEA restart remain explicit user actions;
the build process will not replace the currently installed plugin.
