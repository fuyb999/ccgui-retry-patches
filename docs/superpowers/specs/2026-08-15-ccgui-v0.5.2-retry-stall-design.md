# CC GUI v0.5.2 Codex Retry And Silent Stream Design

## Status

Approved for implementation on 2026-08-15 through the user's request to build
the previous retry patch on the latest CC GUI release and fix the reported
loading and silent-output failures.

## Goal

Produce a reproducible CC GUI `v0.5.2` plugin that preserves the existing Codex
infinite-retry policy while accurately distinguishing four states:

1. the initial Codex attempt is running but has not produced visible output;
2. a retry is waiting for its fixed 30-second delay;
3. a retry attempt is running but has not produced visible output;
4. normal visible streaming has begun.

The UI must not return to ordinary loading merely because a retry process was
started. It returns to normal streaming only after actual content, thinking, or
message data reaches the WebView.

## Evidence And Root Cause

The installed plugin is based on CC GUI `v0.5`. IDEA logs on 2026-08-15 show
the same Codex thread IDs recurring about 10 minutes and 30 seconds apart. This
matches the patched inactivity timeout plus retry delay and proves that the
backend retry loop is alive.

The current protocol sends `attempt_started` before invoking the next SDK
attempt. `SessionCallbackAdapter` discards the retained retry state at that
point, and the WebView callback converts the event to `null`. The loading view
therefore looks normal before the new attempt has emitted any useful event.
This is the reported false recovery.

The current installed `v0.5` also predates the `v0.5.2` upstream streaming-frame
fix. The `v0.5.2` changelog identifies a failure where in-flight message frames
were discarded whenever newer data was queued, starving tool and result blocks
until stream end. Building on `v0.5.2` retains that upstream repair and addresses
the second reported symptom in which Codex is running but CC GUI shows no output.

## Retry And Attempt Protocol

The bridge continues to emit the versioned `[CODEX_RETRY]` protocol.

Scheduled retries retain the existing shape:

```text
[CODEX_RETRY] {"phase":"scheduled","retryCount":1,"delayMs":30000,"retryAt":...,"reason":{"category":"http_5xx","status":503}}
```

Every SDK attempt emits an attempt state before `thread.runStreamed` is called:

```text
[CODEX_RETRY] {"phase":"attempt_started","retryCount":0}
[CODEX_RETRY] {"phase":"attempt_started","retryCount":1}
```

`retryCount: 0` denotes the initial attempt. Positive values denote retry
attempts. The bridge never forwards prompts, response bodies, headers, stack
traces, or arbitrary error messages in these events.

## State Ownership

### Node Bridge

`message-service.js` emits the initial `attempt_started` state. The retry
coordinator emits positive retry counts after a completed retry delay and before
the next attempt. The existing 10-minute inactivity timeout and 30-second fixed
retry delay do not change.

### IDEA Backend

The parser accepts `attempt_started` with a non-negative safe integer count.
`SessionCallbackAdapter` retains both scheduled and started states so a recreated
WebView restores the truth. It clears the retained state when visible message
data, terminal completion, cancellation, or an error arrives.

### WebView

The WebView retains `attempt_started` instead of mapping it to `null`.

- `retryCount: 0` displays that Codex is running and waiting for output.
- a positive retry count displays that the corresponding retry attempt is
  running and waiting for output;
- `scheduled` keeps the reason and live delay countdown;
- content delta, thinking delta, an accepted message snapshot with visible
  current-turn text/thinking/tool activity, stream end, terminal error,
  cancellation, message clearing, or session transition clears the state.

Historical messages and an empty current-turn assistant placeholder do not
clear the state.

`onStreamStart` does not clear the attempt state because that callback only
proves that an SDK iterable exists. It does not prove that user-visible output
has arrived.

## Error And Cancellation Behavior

Capacity, transient HTTP 429, HTTP 500-599, network failures, and inactivity
remain infinitely retryable. Explicit daily-limit 429 responses and HTTP
400/401/403 remain terminal. Cancellation interrupts an active attempt or retry
delay and never schedules another attempt.

The duplicate-side-effect warning remains unchanged: a failed attempt may have
already run commands or tools before a retry repeats the logical request.

## Testing

Tests must prove:

- `v0.5.2` is pinned and rejected on commit, hash, or patch mismatch;
- the initial attempt emits `attempt_started` with `retryCount: 0`;
- scheduled and started retry events remain sanitized and ordered;
- IDEA retains and replays started state, then clears it on visible messages and
  terminal paths;
- the WebView keeps started state through `onStreamStart`, renders initial and
  retry-attempt labels, and clears only on real data or terminal paths;
- all bridge, WebView, Gradle, workflow, packaging, checksum, and embedded bridge
  verifications pass on `v0.5.2`.
