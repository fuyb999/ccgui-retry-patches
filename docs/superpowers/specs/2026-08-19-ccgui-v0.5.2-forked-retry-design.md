# CC GUI v0.5.2 Forked Retry Design

## Context

CC GUI `0.5.2-retry.5` keeps transient Codex failures visible and retries them
every 30 seconds, but it reruns the submitted turn in the same persisted Codex
thread. A long outage can therefore append many failed turns to one thread and
can make the eventual retry inherit partial output from an earlier attempt.

The first experimental replacement used `codex exec fork <threadId>`. Isolated
testing proved that this command creates a distinct thread file but forks the
latest persisted history. If the source already contains the failed turn, that
turn is copied into every new branch. It does not provide the boundary needed
for reliable retries.

Codex CLI `0.148.0` App Server exposes the required protocol operations:

- `thread/read` returns persisted turns and their status;
- `thread/fork` accepts `lastTurnId`, inclusive; and
- `thread/delete` removes a disposable failed branch.

Protocol reference: <https://learn.chatgpt.com/docs/app-server>

## Goals

- Retry transient 429, 5xx, capacity, network, and inactivity failures forever
  at a fixed 30-second interval.
- Fork every resumed-thread retry from the last turn that was already complete
  before the submitted request began.
- Start a new empty thread for retries when no completed turn exists.
- Delete every failed retry branch before creating the next branch.
- Keep the successful retry branch as the GUI's official thread.
- Recover from a persisted source that already has non-completed turns after
  its last completed boundary.
- Never publish or persist a disposable child ID before that child succeeds.
- Preserve visible retry progress and structured thinking/tool output.
- Avoid repeating completed tool actions when an earlier attempt emitted tool
  activity.
- Publish the change as the version-specific `0.5.2-retry.6` patch and tracked
  ZIP artifact.

## Non-Goals

- Rolling back filesystem, process, network, database, or external MCP side
  effects produced before a request failed.
- Retrying terminal daily-limit, 400, 401, or 403 responses.
- Mutating or deleting the stable source thread after a retry succeeds.
- Supporting Codex SDK or CLI versions older than `0.148.0`.
- Restarting IDEA, stopping active sessions, or installing the new artifact
  automatically.

## Alternatives Considered

### App Server Fork At A Fixed Turn Boundary

Use `thread/read` once to capture the last completed turn, then call
`thread/fork` with that immutable `lastTurnId` for every retry. This is the
selected design because it is the only exposed API that both preserves prior
context and excludes the failed submitted turn.

### CLI `exec fork`

This creates an independent thread but always copies current history. Testing
showed that it can include the failed turn, so it is rejected.

### Same-Thread Resume Or Always-New Threads

Same-thread resume accumulates failed attempts. Always starting empty threads
avoids that pollution but discards established conversation context. Both are
rejected for resumed conversations. A new empty thread remains the correct
fallback only when no completed turn exists to fork through.

## Architecture

### 1. App Server JSON-RPC Adapter

`ai-bridge/services/codex/codex-fork.js` will become a focused App Server
adapter. For each operation it will:

1. launch the exact CLI binary and sanitized environment already held by the
   installed Codex SDK;
2. pass the same config overrides and custom base URL as the SDK;
3. start `codex app-server --stdio`;
4. send `initialize`, wait for its matching response, then send `initialized`;
5. send one `thread/read`, `thread/fork`, or `thread/delete` request;
6. match responses by JSON-RPC request ID while ignoring unrelated
   notifications; and
7. continuously drain stderr without retaining its content; and
8. close the child process on success, failure, or cancellation.

Protocol failures are represented by a retryable bridge error without copying
raw stderr, credentials, prompts, or JSONL content into GUI status messages.
Malformed responses, premature process exit, spawn errors, and inactivity all
enter the existing 30-second retry loop.

The adapter does not use `codex exec fork`, directly edit JSONL files, or infer
turn boundaries from filenames.

### 2. Immutable Stable Boundary

Before the original request starts, a resumed conversation is read with
`includeTurns: true`. The coordinator selects the last turn whose status is
exactly `completed` and stores this pair for the complete logical request:

```text
stableSourceThreadId
stableLastCompletedTurnId
```

The pair never changes after the first outbound turn starts. If that first
turn appends `failed`, `interrupted`, or `inProgress` history to the source,
every later fork still uses the original completed ID and excludes all newer
turns.

Boundary discovery also records whether the persisted source already contains
turns after the selected completed turn. This indicates a prior bridge/IDE
shutdown or failed submission. In that case the coordinator does not resume the
dirty source for its nominal first attempt; it forks through the fixed boundary
before making any outbound submission.

If boundary discovery itself fails, the request has not started. The failure
is shown as a retry and boundary discovery is attempted again after 30 seconds.
The retry counter therefore remains distinct from a `requestStarted` flag; a
setup failure must not accidentally trigger a fork or duplicate an outbound
turn.

### 3. Retry Attempt Lifecycle

For a source with a completed boundary:

1. Run the user's first attempt on a clean source thread, or fork first when
   boundary discovery found trailing non-completed history.
2. On a retryable failure, wait 30 seconds.
3. Fork the immutable source through the immutable completed turn.
4. Resume the returned child ID through the existing TypeScript SDK and submit
   the same input.
5. If it fails, delete that child before the next fork.
6. If it succeeds, retain it and make its ID the current GUI thread.

For a new conversation, or a source with no completed turn, each retry uses
`codex.startThread(threadOptions)`. A failed branch is deleted once its
`thread.started` event reveals its ID. No retry falls back to the original
failed thread.

Failed deletion is a barrier, not a warning-only cleanup. The next loop first
retries that deletion; it cannot create another branch until cleanup succeeds.
Deleting an already absent branch is treated as successful so an acknowledged
response lost during transport cannot deadlock retries.

The stable source is retained after success. App Server deletion can remove
descendants, so deleting the source would risk removing the successful branch
or unrelated child work.

`thread.started` from a disposable retry updates only bridge-internal replay
state. It is not emitted as `[THREAD_ID]` while the attempt is running. After
the event stream reaches `turn.completed` and closes without error, the bridge
publishes that child ID before completing the GUI stream. If the stream closes
without `turn.completed`, it is a retryable `SERVER_ERROR` and the child enters
the normal cleanup barrier. This prevents a failed/deleted child ID from being
written into the tab's persisted session state.

### 4. Side-Effect Mitigation

When any attempt has emitted tool activity, subsequent retry input is prefixed
with:

```text
[CC GUI retry recovery] A previous attempt may have completed some tool actions.
Inspect the current workspace and session state first.
Do not repeat actions that are already complete.
```

This reduces duplicate filesystem and external operations but is not a
transactional rollback. External MCP calls, database writes, network requests,
and started processes may already have taken effect. The GUI must not claim
that forked retry makes those operations exactly-once.

### 5. Version Contract

`SdkDefinition.CODEX_SDK` will require `0.148.0` or newer and use `0.148.0` as
its pinned fallback. An incompatible SDK is terminal configuration failure at
startup; the bridge will not silently return to same-thread retry behavior.

## State Transitions

```text
resolve boundary -> original attempt
                       |
                       v transient failure
visible 30s wait -> cleanup pending failed branch -> fork/start -> SDK attempt
                         ^                               |
                         |                               v transient failure
                         +-------------------------------+

successful branch -> current GUI thread -> normal loading/completion
terminal response  -> existing error path
manual cancellation/plugin shutdown -> abort child processes and exit
```

Retry status remains one logical GUI message. `scheduled` shows the countdown;
`attempt_started` switches back to normal loading while the forked SDK request
is active.

## Error Handling

- 429 request-rate errors, all 5xx responses, capacity errors, recognized
  network failures, and inactivity timeouts retry indefinitely.
- A 429 containing `DAYLY_LIMIT_EXCEEDED`, `DAILY_LIMIT_EXCEEDED`,
  `DAILY_USAGE_LIMIT_EXCEEDED`, or `daily usage limit exceeded` terminates.
- 400, 401, 403, and all other explicit 4xx responses terminate.
- App Server read, fork, and delete failures are converted to retryable setup
  failures and retried after 30 seconds.
- A source with trailing non-completed turns is forked before its first new
  submission.
- An SDK stream that ends without `turn.completed` is retryable and cannot be
  promoted to the GUI thread.
- A fork response without a distinct non-empty thread ID is rejected.
- A `lastTurnId` is never omitted when forking a source with failed history.
- No raw API error body, authorization header, prompt, or persisted session
  content is emitted in retry progress.

## Testing

### App Server Adapter

- Assert the exact initialize handshake and request ordering.
- Assert `thread/read` selects only the last `completed` turn.
- Assert `thread/fork` always sends both the stable source ID and stable
  `lastTurnId`.
- Assert the returned child is resumed with the existing SDK thread options.
- Assert `thread/delete` is used for failed children and treats an absent child
  as cleaned.
- Assert malformed JSON, mismatched IDs, RPC errors, premature exit, and abort
  close the process and return retryable errors.
- Assert App Server stderr is drained without retaining its content.
- Assert SDK secrets and stderr details do not appear in retry lifecycle lines.

### Message Coordinator

- Boundary-read failure retries boundary read without starting an SDK turn.
- A dirty source forks before the first outbound turn.
- A first failed resumed attempt is followed only by fixed-boundary forks.
- Three failed retries all use the same source and `lastTurnId`.
- Failed child cleanup completes before the next child is created.
- Cleanup failure retries cleanup without creating an additional branch.
- A new conversation starts a fresh thread on every retry and deletes failed
  child IDs.
- A successful child becomes `state.currentThreadId` and is not deleted.
- Failed child IDs never cross `[THREAD_ID]`; the successful child is published
  only after complete stream processing.
- A child stream without `turn.completed` is deleted and retried.
- Tool activity adds the recovery instruction; text-only failures do not.
- Terminal status and daily-limit tests remain unchanged.

### Live Protocol Verification

Using the installed `0.148.0` CLI and an isolated existing completed session,
verify without printing message content that:

- `thread/read(includeTurns=true)` reports the source turn count;
- a fork through an earlier completed turn has exactly that prefix count;
- the source file and turn count remain unchanged;
- the child ID and rollout file differ from the source; and
- `thread/delete` removes only the disposable child.

## Acceptance Criteria

- No retry path invokes `codex exec fork` or retries through the failed source
  thread.
- Every resumed-thread fork request contains the immutable last completed turn
  ID captured before the first outbound attempt.
- A persisted dirty source is never resumed past that boundary.
- No-history retries use distinct fresh thread IDs.
- Failed branches cannot accumulate during an extended outage: cleanup is
  completed before another branch is created.
- The successful branch becomes the GUI's persistent thread and keeps normal
  structured thinking/tool event processing.
- No failed or incomplete child ID is persisted by Java or the WebView.
- Retry remains visible every 30 seconds and never terminates for a classified
  transient error.
- Daily limit, 400, 401, and 403 still terminate.
- The versioned patch applies cleanly to upstream `v0.5.2`, and the tracked
  `retry.6` artifact passes all verification checks.

## Release

The patched plugin version is `0.5.2-retry.6`, with artifact
`dist/ccgui-0.5.2-retry.6.zip`. Installation and IDEA restart remain explicit
user actions after verification.
