# CC GUI v0.5.2 Long-Session JCEF Stability Design

## Context

CC GUI `0.5.2-retry.4` can make IntelliJ IDEA's JCEF surface unresponsive when
restoring or refreshing a large Codex session. The observed failure loaded
47,917 frontend messages and sent a 97,487,377-character `updateMessages`
payload to JCEF. The WebView heartbeat then stopped, the watchdog attempted a
reload followed by a recreate, and JetBrains remote JCEF threw a
`NullPointerException` while creating a new message router. CC GUI consequently
showed its terminal `toolwindow.jcefRemoteSolution` panel asking for a complete
editor restart.

The upstream Codex request remained alive. The failure occurred in local
history replay and WebView recovery, not in the remote model API or retry
classification.

## Goals

- Prevent automatic Codex restore and `session_updated` reconciliation from
  materializing a complete large JSONL transcript in Java memory.
- Prevent the first WebView synchronization for a long conversation from
  serializing and injecting the complete message list.
- Preserve the latest assistant message, including thinking and tool-use
  blocks, when the transported tail contains only tool results.
- Keep the existing paginated history-panel flow so older turns remain
  available on demand.
- Preserve the retry behavior and visible retry state from `retry.4`.
- Publish the fix as a reproducible, versioned `0.5.2-retry.5` artifact.

## Non-Goals

- Changing Codex retry status classification, intervals, or terminal errors.
- Changing the Codex JSONL format or deleting/truncating session files.
- Disabling the WebView watchdog.
- Working around the JetBrains remote JCEF null dereference inside the IDE.
- Restarting IDEA, stopping active sessions, or installing the artifact
  automatically.

## Root Cause

Two independent safeguards did not cover the first long-session snapshot:

1. `CodexSDKBridge.getSessionMessages()` called
   `CodexHistoryReader.getSessionMessagesAsJson()`. That path accumulated every
   JSONL record, serialized the complete collection, parsed it back into a
   `JsonArray`, converted all records, and retained all converted messages in
   `SessionState`.
2. `StreamMessageCoalescer.selectMessageTransport()` required a previously
   delivered snapshot before enabling tail transport. A first snapshot was
   therefore always full, even when it contained tens of thousands of
   messages.

The 30-turn paginated history loader did not cause the 97 MB transfer. It
already streams the JSONL and sends bounded batches directly to the WebView.
The full transfer came from persisted-tab restore or a later
`session_updated` reload through `loadFromServer()`.

## Design

### 1. Bounded Automatic Replay

Add a streaming recent-message reader alongside the existing full-history
export path. It will feed records from
`CodexHistoryReader.forEachSessionMessage()` into the established Codex
frontend accumulator and retain:

- the latest 180 converted frontend messages; and
- the latest assistant message as a single anchor when it falls before that
  tail.

The bound applies to the converted frontend list, not raw JSONL records, so
duplicate user-record handling and normalized thinking/tool blocks remain
consistent with the current history loader. The retained assistant object is
the same object seen by usage restoration, allowing later token-count records
to update its usage metadata without another full-history pass.

`CodexSDKBridge.getSessionMessages()` will use this bounded streaming method.
The existing `getSessionMessagesAsJson()` method remains unchanged for explicit
history export, where full output is the requested behavior.

This changes persisted-tab restore and background reconciliation from
unbounded memory to at most 181 converted messages while still scanning the
file sequentially for the newest state.

### 2. First-Snapshot Tail Transport

For conversations above the existing long-conversation threshold,
`StreamMessageCoalescer` will select the last 180 messages even when no prior
snapshot has been delivered. It will call `updateMessageTail` with the original
base index instead of building a full JSON payload.

This also protects the history-panel path. That path may retain several
thousand messages for its latest 30 turns, but the first coalescer update after
the user resumes the session will patch only the displayed tail rather than
reinserting the entire page into JCEF.

The coalescer still records the complete Java snapshot as its prefix baseline.
Later growing snapshots therefore continue to use the existing identity-based
stable-prefix check. A replacement or compaction keeps the existing full-rebase
semantics; automatic Codex replay is already bounded before it reaches that
path, so those rebases remain small.

### 3. Sparse Assistant Anchor In A Tail-Only WebView

`updateMessageTail` already accepts an optional assistant anchor and its
original index. Today it can patch that anchor only when the WebView already
holds the full prefix. After a WebView reload, the prefix is empty and the
anchor is silently discarded.

The frontend will explicitly track a sparse assistant anchor when no full
prefix is available:

- With an anchor, render the current prepended history, the single anchor, and
  the transported tail.
- On the next tail update, replace the sparse anchor with the newly supplied
  anchor rather than accumulating duplicates.
- When the assistant moves into the tail, remove the separate sparse anchor.
- Clear sparse-anchor metadata on a full snapshot, session clear, or history
  replacement.

The sparse anchor remains a display-only frontend entry. The backend base index
continues to describe the contiguous tail, and no placeholder array is created
for omitted messages.

### 4. Watchdog Behavior

The watchdog remains enabled. Avoiding the oversized transfer should keep the
renderer responsive and prevent recovery from reaching the JetBrains remote
JCEF recreate path. Existing terminal handling remains as a final fallback for
an independently unhealthy JCEF process.

No retry loop will be added around the remote JCEF null dereference because the
current evidence shows repeated recreation against the same failed CefServer
cannot recover without restarting IDEA.

## Data Flow

### Persisted Tab Or Background Reload

1. `SessionMessageOrchestrator.loadFromServer()` requests Codex messages.
2. `CodexSDKBridge` streams the JSONL and retains at most 180 tail messages plus
   one assistant anchor.
3. `SessionState` receives the bounded list.
4. `StreamMessageCoalescer` sends a normal bounded snapshot because the list is
   below the long-conversation threshold.

### History Panel Resume

1. `HistoryMessageInjector` keeps its existing 30-turn paginated load and
   batched WebView injection.
2. Session state may contain a long page.
3. The first coalescer update sends `updateMessageTail`, not a full snapshot.
4. The frontend patches its existing page or reconstructs a tail-only view
   after a WebView reload.

## Error Handling

- Invalid tail sizes fail fast with `IllegalArgumentException` in the helper.
- Missing or unreadable Codex session files follow the current bridge behavior:
  log the failure and return an empty list.
- A malformed optional assistant anchor does not reject the valid tail.
- Stale sequence checks and session-transition barriers remain authoritative.
- No raw history content, credentials, or complete JSONL lines are added to
  logs. Diagnostics report only counts, payload sizes, indexes, durations, and
  sequence numbers.

## Testing

### Java

- A large Codex fixture returns only the last 180 messages plus an omitted
  assistant anchor from `CodexSDKBridge.getSessionMessages()`.
- The bounded reader preserves tool-use/tool-result normalization and usage
  attached after an assistant record.
- The first long `StreamMessageCoalescer` snapshot selects a tail transport.
- A first long snapshot carries an assistant anchor when the tail omits it.
- Existing stable-prefix, compaction, stream-end, and provider-history tests
  remain green.

### WebView

- An empty or recreated WebView renders a supplied sparse assistant anchor
  before the tail.
- Repeated tail updates replace, rather than duplicate, the sparse anchor.
- An anchor is removed when the assistant becomes part of the tail.
- Full snapshots and session clears reset sparse-anchor metadata.
- Existing history prepend, sequence barrier, retry indicator, and structured
  tool/thinking tests remain green.

### Artifact

- Run all focused Node, WebView, and Gradle tests, followed by the complete
  patch workflow.
- Verify the ZIP integrity, embedded plugin version, bridge signature, WebView
  protocol markers, and SHA-256 checksum.
- Track `dist/ccgui-0.5.2-retry.5.zip` and its checksum on `main`.

## Acceptance Criteria

- Automatic replay of the observed 47,917-message session cannot return more
  than 181 converted messages to `SessionState`.
- No first long-session WebView update uses the full `updateMessages` payload.
- The latest assistant thinking and tool-use blocks remain visible when more
  than 180 later tool results exist.
- Existing older-history pagination remains usable.
- Retry rules remain unchanged: transient 429 and 5xx errors retry; daily-limit,
  400, 401, and 403 errors terminate according to the existing patch contract.
- The build is reproducible from the pinned upstream `v0.5.2` source and the
  version-specific patch.

## Release

The patched plugin version will be `0.5.2-retry.5`, with artifact
`dist/ccgui-0.5.2-retry.5.zip`. Installation and IDEA restart remain explicit
user actions after verification.
